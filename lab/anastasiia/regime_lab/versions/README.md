# Модель `anastasiia_plan_hull` і її три версії

Планувальник у вікні 26 тижнів: LP у режимах симулятора, ціна цілого тижня в самому LP («оболонка») і оцінка кінця
вікна з межею в 1 тиждень спалювання. Метод описано в `../README.md`, історію — у `hub/tried/mpc.md` (розділи
`regime_lab`, `plan_lab` і «Порівняння двох підходів…»).

Три версії — це одна модель; різниться лише те, скільки вона рахує за тиждень.

| версія | налаштування | що робить щотижня | де лежить |
| --- | --- | --- | --- |
| **повільна** | `plan_hull.json` | два розв'язки LP: з оболонкою і точний; без годинника | `agents/anastasiia_plan_hull` (у git) |
| **швидка, без годинника** | `plan_hull_fast.json` | один розв'язок LP: оболонка раз на два тижні, і того тижня грається сам розв'язок з оболонкою (перший тиждень у ньому точний); план самих правил для якоря програється раз на чотири тижні | збирається з джерела |
| **швидка, з годинником** | `plan_hull_fast_clock.json` | те саме і власний таймер: межа 0.7 бюджету тижня (1.4 с на Small, 2.8 с на Full), один розв'язок не довший за 3 с; якщо розв'язок не встиг, грається план, перенесений із минулого тижня | збирається з джерела |

Жодну зі швидких версій не відправлено на борд і не оцінено на формальному наборі (root 222). На root 222 оцінюється
лише повільна; її рядок — у `hub/FORMAL_RESULTS.md`.

## Як зібрати версію і перевірити її

```bash
# зібрати теку моделі з джерела лабораторії (швидкі версії; повільна вже лежить в agents/)
uv run python lab/anastasiia/regime_lab/build.py --name=plan_hull_fast_clock --agent=anastasiia_plan_regime \
    --params="$(cat lab/anastasiia/regime_lab/versions/plan_hull_fast_clock.json)"
# тека: outputs/regime_lab/agents/plan_hull_fast_clock

# перевірки сервера і час тижня в копії серверного контейнера (1 dev-епізод; --docker_episodes=3 — три)
uv run sbf check outputs/regime_lab/agents/plan_hull_fast_clock --task=small --docker
uv run sbf check outputs/regime_lab/agents/plan_hull_fast_clock --task=full --docker
uv run sbf check agents/anastasiia_plan_hull --task=full --docker
```

`sbf check --docker` друкує час першого тижня, медіану й максимум CPU-секунд тижня в контейнері і тижні понад
бюджет (2 с на Small, 4 с на Full).

## Дешеве прискорення повільної версії (перевірено 8 жовтня, не взято)

Повільна версія з двома перемикачами: перший розв'язок тижня без кросоверу (`hull_rough`) і план самих правил раз на
чотири тижні (`anchor_every` 4); решта як у `plan_hull.json`. Один прогін на машині розробки, 4 процеси, поза
контейнером, парно до повільної на тих самих епізодах (`versions.py`):

| набір | повільна | прискорена | різниця RSS (90 % інтервал) | дешевша за повільну |
| --- | --- | --- | --- | --- |
| Small 111 ×64 | 0.8724 | 0.8704 | −0.0020 (−0.0045…+0.0003) | у 24 із 64 |
| Full 111 ×32 | 0.9000 | 0.8970 | −0.0029 (−0.0125…+0.0041) | у 21 із 32 |

Час тижня Full у цьому прогоні: медіана 2.51 с проти 3.03 (−17 %), середнє 2.30 проти 2.67, але хвіст майже не
зрушив: 95-й перцентиль 3.66 проти 3.84 с, 99-й 4.91 проти 4.42, понад 4 с 2.9 % тижнів проти 3.4 %. Два прогони
йшли за різного завантаження машини, тож хвости порівнювати можна лише грубо. Висновок: пара знімає час звичайного
тижня, а довгі тижні, які й виходять за бюджет, визначає повільний точний розв'язок LP; запасу щодо ліміту вона
майже не додає, а рахунок трохи нижчий у межах шуму.

## Чого ці числа не показують

- Рахунок виміряно без серверного ліміту часу. На сервері тиждень понад бюджет грає правило naive; скільки коштує
  такий тиждень, не міряно.
- Рахунок версії з годинником залежить від швидкості машини: на повільнішій годинник обриває більше розв'язків.
- Усе це один прогін на одній машині.
